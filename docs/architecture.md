# Architecture and extension points

## Components

The CLI calls the engine with a spec, work mode and iteration budget. The engine records an observation and a small plan, invokes AgentAdapter.generate, and hands the source to the verifier. A failing result goes to AgentAdapter.reflect and becomes feedback for the next generation call. Passing results produce an awaiting_review state. A separate CLI invocation approves or rejects that candidate.

The adapter interface accepts a spec and a list of structured feedback objects. DemoAgent deliberately returns two bundled source variants; its reflection text is scripted. Replacing this adapter alone does not make the execution layer production-ready.

## States and transitions

| State | Allowed next action |
| --- | --- |
| running | Generate and verify within budget |
| needs_human_context | Start a new run with explicit compatibility context |
| iteration_limit | Inspect failures and start a new bounded run |
| awaiting_review | Approve with revalidation, or reject |
| rejected | Inspect and begin a new run if needed |
| delivered | Read the verified local artifact; no automatic deployment |

An approval compares current artifact/spec hashes against the run record, reruns gates and only then writes the delivery file. A run directory is never overwritten by a new generation run. Run records are local files for inspection, not an authenticated audit service.

## Tool boundaries

The example uses local tools: spec loading, candidate writing, Python compilation, syntax-policy validation, subprocess acceptance execution and report writing. It deliberately includes no enterprise MCP connector or database. A future tool adapter should return the same structured gate result contract and use a properly isolated worker with resource and network controls.

The present verifier rejects imports, calls, attributes and statements outside a single expression-returning function. Execution uses a separate Python process with a timeout. This narrower demonstration policy is not a claim of comprehensive sandbox security.

## Persisted evidence

- spec.json: the fictional requirement snapshot and acceptance cases.
- attempt_01.py, attempt_02.py: each proposed candidate.
- run.json: states, results, source snapshots and hashes.
- trace.jsonl: ordered observation, planning, generation, verification, reflection and review events.
- report.html: a standalone view of the same recorded data.
- delivery/booking_policy.py: created only after a passing approval.

The sample under docs/sample-run was generated by the repository commands. Its approval is a scripted local demonstration decision, not an enterprise release approval.
